> **1 部品 = 1 チェック。**[部品1](手順/部品1_完成バーを機械で閉じる.md) B1-03 の成果物。
> 🟥 **このバーは「緑なら完成」ではない。**「**機械が持てる面**」と「**人が見る面**」を割ったもので、

### 罠 3 の詳細 —— これが一番効いた

**`Dialog/Open` は「描画されない story」として `cfg.overrides.Dialog.skip` に入っていた。**
根拠は storybook 自身の `sb-error: no storybook root content` と、`/design-sync` の比較ハーネスの判定。

🟥 **どちらも間違っていた。**2026-08-09 に Playwright で直接見たら、**dialog は描画されている**——

```
#storybook-root  → 空（innerHTML 0 文字）
#radix-_r_0_     → [role=dialog]「開いた状態 / 手5 で overlay とスクリムを目視するための story。/ Close」
```

**`#storybook-root` の外（portal）に出ているだけ。**
検証スタックは全部 `#storybook-root` だけを見ているので、**portal に出る部品は丸ごと観測から消えていた。**
🟨 `.design-sync/NOTES.md` は `Tooltip` について「portal されたツールチップが枠外に落ちて写らない」と気づいていたが、
**`Tooltip` 固有の癖として処理していた。系統的な問題だった。**

🟦 **一方で、範囲を広げても部品の欠陥件数は動かなかった**——`document` 走査で増えた 96 件は
**全部 `region`**（「内容は landmark に含まれるべき」。storybook の iframe に `<main>` が無いことによる **harness 由来**）で、
`region` を除けば root 走査と**完全一致**。→ **面②は `region` を除外して数える。**

## 2. 面①「描画された」の定義

```
story を描いたあと、document に「意味のある中身」が 1 つ以上ある
```

🟥 **`#storybook-root` を見てはいけない**（罠 3）。**`document.body` を見る。**
🟥 **`textContent` の有無で判定してはいけない**——`Spacer` / `Separator` は**文字を持たない部品**で、
文字で測ると「対象 0 件で緑」の逆（**正しい部品を落とす**）が起きる。

**判定**: `document.body` の中に、`#storybook-root` の子孫 **または** portal の子孫として、
**要素が 1 つ以上あり、その少なくとも 1 つが 0 でない大きさを持つ**こと。

## 4. 面③「状態面」の共通の面

| 面 | いつ「対象外」と書けるか |
| --- | --- |
| `default` | **無い部品は無い**（対象外にできない） |
| `hover` | ポインタに反応しない部品（`Spacer` / `Separator` / `Skeleton`） |
| `focus-visible` | フォーカスを受けない部品 |
| `disabled` | 無効状態を持たない部品 |
| `invalid` | 入力を受けない部品 |
| `loading` | 非同期を持たない部品 |
| `empty` | データを受けない部品（`DataGrid` / `ListDetail` は**必須**） |
| `overflow` | 長文・多件数で崩れない（文字を持たない部品は対象外） |

🟥 **「対象外」には理由を書く。**書かない空欄は**埋めたことが緑に見える**（[CLAUDE.md](../CLAUDE.md)「まだ作らないと決めるときは理由を書く」の状態版）。
🟥 **`hover` を CSS クラスの偽装で描かない**——**実際に `page.hover()` して撮る**
（[DR-0054](DR/DR-0054-mock-specimens-cannot-reproduce-stacked-states.md)：モックの検体は積み重なった状態を再現できない。手5 で 1 度踏んだ）。

**現況**: 🟥 **`States` 相当を持つのは 39 部品中 2 件**（`Checkbox` / `Input`）。

## 5. 面④「語彙の効果」

```
語彙 prop を指定したら、実効値（getComputedStyle / getBoundingClientRect）がその語のとおりになる
```

🟥 **「指定した」ではなく「効いた」を測る。**[DR-0090](DR/DR-0090-token-classes-were-silently-dropped-by-tailwind-merge.md) の実測——
`SelectTrigger` の `width` は **3 語とも一度も効いていなかった**（`twMerge('w-fit w-field-md')` が両方残し、CSS 順で `w-fit` が勝つ）。
**prop も型も lint も story も緑で、作用だけが無かった。**

🟨 **語彙を 1 語足したら `src/lib/tw-merge.ts` にも足す**——**語彙の写しが `tokens.css` と 2 箇所にあり、機械で守られていない**（工程外の修正が残した宿題 ①）。

### 🆕 面④ の測り方（部品2 C2-05 で実装した・2026-08-09）

**story の `play` 関数**で測る。**バーの実行エンジン（`pnpm test-storybook`）の中**で走るので、
別スクリプトのように「回し忘れる」経路が無い（部品1 D7 と同じ理由）。

```ts
play: async ({ canvasElement }) => {
  await waitFor(async () => { await expect(width('#sw-sm')).toBe(24) })
  await expect(width('#sw-md')).toBe(32)
  await expect(width('#sw-sm')).not.toBe(width('#sw-md'))  // 語が別の値になっていること
}
```

🟥 **書くときの落とし穴 3 つ**（全部 C2-05 で踏んだ）:

1. **`waitFor` で囲む。**同期に測ると **CSS が当たる前の値**を読む。
2. **`expect` は `await` する。**`storybook/test` の `expect` は Promise を返すので
   付けないと `no-floating-promises` が出る（🟦 実行時は instrumenter が await するので**落ちはする**）。
3. ★★★ 🟥 **`vitest.config.ts` に `@tailwindcss/vite` が要る。**
   無いと **CSS が 1 行も当たらず、正しい部品を落とす**（[DR-0094](DR/DR-0094-the-bar-engine-ran-without-any-css.md)）。
   **1 と 2 を直しても直らないので、まず 3 を疑う。**

🟨 **単調性まで測る**——`SelectTrigger` の 3 語は **sm > lg の逆転**だった（[DR-0090](DR/DR-0090-token-classes-were-silently-dropped-by-tailwind-merge.md)）。
「値が入っている」ではなく「**語の順序どおりに並んでいる**」を見る。

## 7. 🟥 このバーが保証しないこと

- **44px の当たり判定**（面⑥・axe は 24px AA しか測らない）
- **意味の妥当性**（面⑦・「その部品がその役割か」は人が見る）
- **`serious` の a11y**（台帳に載せるだけ。落とさない）
- ★ **「緑 = 良い部品」ではない。**このバーは**壊れていないことの下限**であって、上限ではない。

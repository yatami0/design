# データモデル

> 工程2（データの器）の成果物。[手順書](手順/工程2_データの器_MSWとデータモデル.md) §0 **Q1 の答えはこの文書の §4**。
> 実測の時系列は [実行記録 §工程2](実行記録.md)。

**この文書は「題材（Redmine）」の側の文書である。**コア（使い回す部品）はここに書かれた語彙を知らない
（[段取り §0b](工場の段取り.md)）。境界の置き方は §6。

## 1. なぜこの文書があるか

5 画面（一覧 / 詳細 / ガント / EVM / 稼働表）は**同じチケットデータの別の見方**なので、
画面を作る前に「**何が取れて、何が取れないか**」を 1 枚にしないと、
**取れないものを前提にした画面**を作ってしまう。とくに EVM は
「Redmine にあるように見えて無い」項目が多い（§4）。

🟥 **モックは「Redmine が返せるもの」しか返さない。**返せないものをモックが返すと、
実 API に繋いだ日に画面が壊れる——それは**モックが嘘をついた**ということになる。
この規律が手順書の Q3（実 API に繋ぐとき何が書き換わるか）を測れる形にしている。

## 2. Redmine が返すもの（一次情報・2026-08-07 取得）

> 🟦 = 公式 wiki に明記あり ／ 🟨 = 版によって出る（wiki に一覧が無い）／ 🟥 = 無い

### 2.1 Issue（`GET /issues.json`・`GET /issues/:id.json`）

| フィールド | 形 | 印 |
| --- | --- | --- |
| `id` | number | 🟦 |
| `project` / `tracker` / `status` / `priority` / `author` / `assigned_to` / `category` / `fixed_version` | **`{ id, name }` の入れ子** | 🟦 |
| `subject` / `description` | string | 🟦 |
| `start_date` / `due_date` | `YYYY-MM-DD` | 🟦 |
| `done_ratio` | number（0〜100・**10 刻み**が既定） | 🟦 |
| `estimated_hours` | number \| null | 🟦 |
| `spent_hours` | number | 🟨 **単票では返る**（wiki の一覧に無い） |
| `parent` | `{ id }` | 🟦 |
| `custom_fields` | `[{ id, name, value }]` | 🟦 |
| `created_on` / `updated_on` | ISO 8601 | 🟦 |
| ページング | `total_count` / `offset` / `limit` を**封筒**に持つ | 🟦 |

★ **重要な形の違い**: ステータスも優先度も**列挙型ではなく `{ id, name }`**。
現行の `src/lib/fixtures/issues.ts` は `status: 'new' | 'inProgress' | …` の**自作 union** で、
**Redmine の形ではない**（手4 D1=A の使い捨て）。→ §5 の 2 層で吸収する。

★★ **`include` の許容値が 2 つの端点で違う**（一次情報を逐語で確認した）:

| 端点 | `include` に書ける値 |
| --- | --- |
| `GET /issues.json`（一覧） | `attachments` / **`relations`** の **2 つだけ** |
| `GET /issues/:id.json`（単票） | `children` / `attachments` / `relations` / `changesets` / **`journals`** / `watchers` / `allowed_statuses` |

🟥 **`journals`（変更履歴）は単票でしか取れない。**これが §4 の欠落 ② の出どころ。

### 2.2 TimeEntry（`GET /time_entries.json`）

| フィールド | 形 | 印 |
| --- | --- | --- |
| `id` / `project{id,name}` / `issue{id}` / `user{id,name}` / `activity{id,name}` | | 🟨 wiki に応答例が無い（POST の引数だけ記載）。**版で確認が要る** |
| `spent_on` | `YYYY-MM-DD` | 🟦（POST 引数として明記） |
| `hours` | number | 🟦 |
| `comments` | string（255 字） | 🟦 |

🟦 **AC（実績）だけは素直に日次で取れる。**`spent_on` があるので `user × 日` にも `issue × 日` にも畳める。

### 2.3 IssueRelation（`GET /issues.json?include=relations` ほか）

`{ id, issue_id, issue_to_id, relation_type, delay }`。
`relation_type` は **10 値**: `relates` / `duplicates` / `duplicated` / `blocks` / `blocked` /
`precedes` / `follows` / `copied_to` / `copied_from`（既定 `relates`）。
`delay` は **`precedes` / `follows` のときだけ意味を持つ**（例の JSON では `null`）。

🟦 **ガントの依存線に要るものは揃っている**——しかも**一覧の `include` で取れる**（上表）。

### 2.4 Version（`GET /projects/:id/versions.json`）

`{ id, project, name, description, status, due_date, sharing, created_on, updated_on }`
＋ 詳細では `estimated_hours` / `spent_hours`。
`status` = `open` / `locked` / `closed`。`sharing` = `none` / `descendants` / `hierarchy` / `tree` / `system`。

🟦 **ガントのマイルストーンは `version.due_date` で引ける。**

### 2.5 その他

`GET /projects.json`（`{ id, name, identifier, description, parent, status, created_on, updated_on }`）／
`GET /users.json`（`{ id, login, firstname, lastname, mail, created_on }`。🟥 **表示名は連結して作る**）／
`GET /enumerations/issue_priorities.json`・`time_entry_activities.json`。

## 3. 画面 × 必要なデータ

| 画面 | 主に読むもの | 取得の形 |
| --- | --- | --- |
| ① 一覧 | Issue（+ フィルタ・ページング） | `GET /issues.json?...&offset&limit` |
| ⑤ 詳細（編集あり） | Issue 単票 ＋ `journals` ＋ 選択肢（status / priority / user / version） | `GET /issues/:id.json?include=journals` ＋ `PUT /issues/:id.json` |
| ② ガント | Issue（`start_date` / `due_date` / `done_ratio` / `parent`）＋ relations ＋ versions | `GET /issues.json?include=relations` ＋ `GET /projects/:id/versions.json` |
| ③ EVM | Issue（`estimated_hours` / `done_ratio` / 期間）＋ TimeEntry の日次 | `GET /issues.json` ＋ `GET /time_entries.json?from&to` |
| ④ 稼働表 | TimeEntry を `user × 日` に畳む ＋ users | `GET /time_entries.json?from&to&user_id` |

## 4. ★ Q1 の答え — 足りないもの（差集合）

**EVM とガントに必要なデータの形**を Redmine の上に並べると、**5 つ足りない**。
🟥 **足りないものは「モックで作れば済む」ものではない**——モックで作ると、実 API に繋いだ日に消える。

| # | 足りないもの | 何に効くか | 実 API では | この工場での扱い |
| --- | --- | --- | --- | --- |
| **①** | ★★ **ベースライン（計画の凍結）** | EVM の **PV**・スケジュール差異 | 🟥 **無い。**`start_date` / `due_date` / `estimated_hours` は**現在値**で、変更すると**過去の PV も書き換わる**（計画が実績を追いかけ、SV が構造的に 0 に寄る） | 🟨 **PV は「現在の計画からの按分」で始める**（= 実 API でも同じ計算ができる形）。「凍結された計画」は Redmine の外の概念なので、**工場側で持つかどうかは工程7 の判断**（D10） |
| **②** | ★★ **進捗（`done_ratio`）の日次履歴** | EVM の **EV** の時系列 | 🟥 **一覧では取れない。**履歴は `journals` にあるが **`include=journals` は単票専用**（§2.1 の逐語確認）。60 件の EV 曲線には**60 リクエスト**要る | 🟨 **モックも同じ制約を再現する**（一覧に journals を混ぜない）。EV 曲線の作り方は工程7 で決める——**「重い」ことが設計判断の材料そのもの** |
| **③** | **金額・単価** | EVM を「円」で出すこと | 🟥 **標準に無い**（プラグイン領域） | 🟦 **EVM は「時間（h）」で回す。**単位を決めるのは画面ではなくこの文書 |
| **④** | **稼働可能時間（capacity）と非稼働日** | 稼働表の「予定 / 空き」・ガントの日数計算 | 🟥 **無い**（ユーザの標準労働時間も、祝日カレンダーも API に無い） | 🟨 **稼働表は当面「実績のみ」**。予定列を出すなら**工場側の定数**（例: 1 日 8h・土日を除く）で、**Redmine 由来ではないと画面に明示する** |
| **⑤** | **表示用の色・トーン** | `StatusPill` の tone、ガントのバー色 | 🟥 **無い。**`status` は `{ id, name }` だけで、意味論（進行中 / 完了）を持たない | 🟦 **`status.id → tone` の対応表は題材側（`src/redmine/`）が持つ。**コアの `StatusPill` は tone しか知らない（§6） |

> 🟦 **逆に、ガントに必要なものは全部ある**（開始 / 期限 / 進捗 / 親子 / `precedes`＋`delay` / マイルストーン）。
> **ガントが最重なのはデータではなく描画**——工程6 の Q2（既製品か自作か）が本体であることが、この差集合で裏づいた。

## 5. 我々の 2 層（D1）

```
Redmine の API 表現            変換の境界              画面が使う型
src/redmine/types.ts   ──▶  src/redmine/convert.ts  ──▶  src/redmine/model.ts
（snake_case・{id,name}）      （★ ここだけが実 API で書き換わる）   （camelCase・tone 付き）
```

- **`types.ts`** は Redmine の JSON をそのまま写す。**手を加えない**（加えると「実 API では何が来るか」が分からなくなる）
- **`convert.ts`** が唯一の変換点。**Q3 の答えを「ここだけ」に設計している**
- **`model.ts`** は画面の型。`assignee: { id, name }`・`status: { id, name, tone }` のように**表示に要る形**まで持つ
- **`client.ts`** が URL の形を知る唯一の場所（`/issues.json` を書いてよいのはここだけ）

## 6. コア / 題材の暫定境界（[未決 #6](工場の段取り.md) への材料）

**固有物はこの工程で最初に現れた。**規則の起草は工程3 に残すが、暫定の線は**ディレクトリ**で引いた。

| | 置き場 | 出荷（`src/index.ts`） | 例 |
| --- | --- | --- | --- |
| **コア** | `src/components/**` `src/patterns/**` `src/templates/**` `src/styles/**` | 🟦 **する** | `StatusPill`（tone しか知らない）・`DataGrid` |
| **題材** | `src/redmine/**` `src/mocks/**` | 🟥 **しない**（1 つも export しない） | `status.id → tone` の対応表・`/issues.json` の URL |

★ **`StatusPill` が良い検体になった**——コアは「tone」という**有限の語彙**しか知らず、
「Redmine の status 5 番が完了である」という知識は題材側にある。
**この形（コアは語彙、題材は対応表）が判定規則の候補**。工程3 で他の固有物に当ててみる。

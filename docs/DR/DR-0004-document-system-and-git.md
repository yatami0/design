# DR-0004: 証跡は 4 層に分ける（段取り / 手順書 / 実行記録 / DR）+ git 運用

## 背景

手0 を記録し手1 を計画する段階で、記録形式が必要になった（＝必要性が 2 回証明された）。PoC の `docs/procedures/_template.md` と CC-Skills の phase ファイルという 2 つの既存形式があった。

## 決定

### 文書の責務

```
段取り（UI検証の位置づけと段取り.md）  … 何を・なぜ・どの順で。全体の地図
  └ 手順書（docs/手順/手N_*.md）      … その手で「答えを出す問い」と作業計画。実測は書かない
      └ 実行記録（実行記録.md）        … 実測結果の時系列。手ごとの構成とゲート結果
          └ DR（docs/DR/DR-00XX-*.md） … 1 決定 or 1 発見。横断で引ける粒度
```

1. **手順書と実行記録を混ぜない。**計画と結果を同じ場所に書くと二重管理になるか、計画が結果に上書きされて「何を確かめようとしたか」が消える。
2. **手順書の §0 は「この手で答えを出す問い」**を最上位に置く。本 repo の成果物は部品ではなく観測なので、**問いが空ならその手はやらなくてよい**。問いは yes/no か有限の選択肢に落ちる形で書く（「うまくいくか」は問いではない）。
3. **決定も発見も `docs/DR/` に 1 ファイルずつ積む**（`type: decision | finding` で区別）。PoC のように DR と OBS を分けるのは、必要性が 2 回証明されてから。
4. **決定は不変に積む。**覆すときは本文を書き換えず、新しい DR で supersede する。ただし**事実誤認の訂正は本文を直し、訂正した旨を残す**（決定の変更ではないため）。

### git 運用

- `main` が安定点。手ごとに `step/h<N>-<slug>` を切り、完了したら `main` へ `--no-ff` マージ
- コミットは `<type>(H<N>): 日本語要約 [手N]`（type は PoC の規約に合わせる）
- 手に属さない作業（文書整備・証跡整理）は `main` に直接コミットしてよい

## 根拠（実測）

- PoC の手順書テンプレから: ステップの型（目的・実行・期待結果・検証・判断ポイント・詰まったら）、完了条件を機械ゲートのチェックボックスにする規律。
- CC-Skills の phase ファイルから: frontmatter の `status` / **`next_action`**（セッションをまたいで再開できる）、リサーチ出典を節として持つ形。
- PoC との違い: 実行者が Claude であること（PoC は「人が手で実行し Claude は代行しない」）。

## 影響

- 手0 は手順書を持たない（フォーマット確定が手1 の計画時点だったため）。手1 以降は「手順書で問いを立ててから実行する」順序を守る。
- 実行中に手順書 §2 に無い選択肢が出たら、**その場で決めずに §2 へ追記してから進む**（手1 の D9/D10 がその実例）。

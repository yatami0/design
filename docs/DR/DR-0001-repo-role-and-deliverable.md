# DR-0001: 本 repo の役割はワークフロー検証・成果物は「決定 + 移送可能なコード」

## 背景

`~/git/design` を作ったが、何をする場所かが未定だった。「UI 部分を検証する」の主語が 2 つに割れていた——①Redmine 自作 UI の画面そのもの ②UI を作るワークフロー（Figma/Claude Design → shadcn → コード）。

## 決定

1. **主目的は② ワークフローの検証**（ユーザー決定 2026-07-26）。①（画面設計）は後。
2. **成果物は「決定」と「PoC へ移送可能なコード」の両方**（ユーザー決定 2026-07-26）。使い捨ての実験場にはしない。
3. **移送の瞬間だけは人が実行する。**repo 内では Claude が自由に書いてよいが、PoC へ持ち込む操作は人が行う。

## 根拠（実測）

- PoC 全体の目的が「方式が通るか」（`docs/process/PoC実行計画.md` §1）であり、UI もその型に揃うのが自然。
- ① は PoC の S1（要求分析）が未着手で**画面要求が 1 本も無い**（`docs/handoff.md` の進捗ボード）。入力が無い状態で始めると要求が後から来て作り直しになる。
- PoC は hook（`.claude/hooks/block-product-edit.mjs`）で `apps/**` `packages/**` への Claude の編集を止めている。`shadcn add` は「コードを自分の repo に置く」行為なので PoC 内では全工程が人の手作業になる。**Claude と一緒に UI を高速で試行できる場所は構造上ここしかない**——これが本 repo の存在理由。

## 影響

- 決定3 が無いと、本 repo は PoC の「成果物は人が作る」規約の**抜け道**になる。線の引き場所を手9（移送手順）で明文化する。
- ① をやるなら PoC 側で S1 を先に回す必要がある（順序の制約）。

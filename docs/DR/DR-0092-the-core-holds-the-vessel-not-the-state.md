# DR-0092: コアは器を持ち、状態は持たない

## 背景

工程4（編集）で **[段取り 未決 #4](../工場の段取り.md)「編集の状態管理の置き場」**に答える必要が出た。
段取りは選択肢を **「shadcn の `Form`（react-hook-form ＋ zod）／自作」の二択**で書いていたが、
手順書起こしの実測で**その二択が不完全**だと分かった。

| shadcn の item | 引く外部依存 |
| --- | --- |
| `form` | 🟥 **`react-hook-form` / `zod` / `@hookform/resolvers`** |
| **`field`**（フォーム 1 枠の器） | 🟦 **0 件**（`registryDependencies` は `label` / `separator` で両方在庫） |

**「器だけ入れる」という第 3 の選択肢が実在した。**

## 決定

**コアは器を持ち、状態は持たない。**

1. **コア（`src/components/**` `src/patterns/**` `src/templates/**`）はフォームの見た目だけを持つ**——
   ラベルの位置・必須の印・説明文とエラー文の置き場・送信行の並び。
   エラーは **`error?: string`（ただの文字列）**で受け取り、**検証の仕組みを知らない**。
2. **編集の状態管理（react-hook-form）と検証（zod）は題材の層（`src/redmine/**`）が持つ。**
3. **`react-hook-form` / `zod` / `@hookform/*` は `devDependencies`。**
   出荷物が要求しないものを `dependencies` に置かない——**依存表は出荷物の名乗り**。
4. **上の 1〜3 を機械で守る**——コア 3 層からの状態ライブラリ import を
   `no-restricted-imports` で禁止する（`eslint.config.mjs` の `noFormStateLibs`）。

### ★ 一般則（この決定より広い）

🟦 **ユーザー判断（2026-08-08）の理由は逐語で「UI はできるだけ純粋に保つ」。**
これは D1 だけの話ではないので、**出荷物に依存を足すかどうかの判定に一般化して使う**:

> **出荷物に依存を 1 件足すことは、「このデザインシステムを使う repo 全部がその依存を取る」ことと同じ。**
> 足す前に、**器（依存 0）で済む形が無いか**を先に探す。

🟥 **工程6（チャート・ガントの素材源）はこの規約が正面から効く工程**なので、申し送る。

## 根拠（実測）

### ① 判定規則（[DR-0088](DR-0088-core-subject-boundary-is-decided-by-two-questions.md) の 2 問）を当てた

| 問 | 「フォームの状態管理」への答え |
| --- | --- |
| ① Redmine を知らない repo でも意味が通るか | 🟦 **通る**（コア候補） |
| ② 見た目・振る舞いの選択を有限の語で言えるか | 🟥 **言えない**（フィールドの構成は自由・無限）→ **コアは器だけ、中身は使う側に返す** |

**規則がそのまま B を指した。**これは DR-0088 §影響 の推論
「工程4 で『編集の状態管理』という新種の固有物が来る。2 問で裁けるかが次の検算」の**履行**にあたる。

### ② 編集の固有物 12 件に 2 問を当てた（裁けなかったものを名指しする）

| # | 固有物 | 場所 | 2 問で裁けたか |
| --- | --- | --- | --- |
| 1 | 件名は必須・255 文字 | `issueSchema.ts` | 🟦 問 1 で題材 |
| 2 | 進捗は 0〜100 の整数 | 同上 | 🟦 問 1 で題材 |

| 5 | ステータス / 優先度の一覧の**端点** | `client.ts` / `handlers.ts` | 🟦 問 1 で題材 |
| 6 | 変更履歴のフィールド名の対応表（`status_id` → 「状態」） | `IssueDetail.tsx` | 🟦 問 1 で題材（対応表） |

| 11 | 🟥 **どの項目を編集させるか**（件名・状態・優先度・進捗・説明・コメントの 6 つ） | `IssueDetail.tsx` | 🟥 **裁けない**（本文） |
| 12 | 🟥 **保存の単位**（1 画面 1 回・変更点だけ・楽観更新なし） | `useIssue.ts` | 🟥 **裁けない**（方針） |

- **裁けた 10 件は「題材の対応表」か「コアの器 / 語彙」のどちらかに落ちた。**
- 🟥 **裁けなかった 2 件は DR-0088 が「本文」と呼んだもの**（画面の合成・既定値・方針）と同じ種類で、
  **新しい種類は出なかった**＝ **2 問は編集でも形を変えずに機能した。**
- 🟨 **ただし 12 が「本文」なのは自明ではない**——「保存の単位」は
  **他所でも意味が通り（問 1 でコア候補）**、**有限の語でも言えそう**（`optimistic` / `pessimistic`）。
  それでもコアに入れないのは、**入れると値の管理をコアが持つことになる**から（本 DR の 1）。
  → 🟥 **2 問だけでは決まらない場合がある**ことの 1 例目として記録する。

### ③ 出荷面で成立を確認した

| 測ったもの | 結果 |
| --- | --- |
| `dist/**` に `react-hook-form` / `@hookform` / `zod` の型名 | 🟦 **0 件** |
| `package.json` の `dependencies` | 🟦 **12 件のまま**（3 件は `devDependencies`） |
| `dist` に題材（画面・スキーマ）が混ざったか | 🟦 **0 件**（JS・`.d.ts`・静的の 3 本とも） |
| コアの器の props に `value` / `onChange` が生えたか | 🟦 **生えなかった**（`FormField` は 6 props で止まった） |
| lint の赤テスト（コア 3 層で rhf / zod / @hookform を import） | 🟦 **3 検体とも発火・題材では緑** |

### ④ 上流の実装がすでにこの形だった

shadcn の `field.tsx` の `FieldError` は
`errors?: Array<{ message?: string } | undefined>` を受けるだけで、**`react-hook-form` を 1 行も import していない**。
rhf の `FieldErrors` は構造的にそのまま渡せる。
→ **「コアは rhf を知らないまま器を提供できる」は我々の発明ではなく、上流がそう作っている。**

## 影響

**観測から直接言えること**

- **フォームの器と値の管理は別の層に置ける**（実装で成立させた）。器の props は 6 つで止まった。
- **`.d.ts` に外部型が出ないこと**を実測で確認した＝ [DR-0072](DR-0072-no-passthrough-of-dependency-types.md) の再演は起きなかった。
- **DR-0088 の 2 問は編集でも機能した**が、**2 問だけでは決まらない例（保存の単位）が 1 件出た。**
- 段取りが立てた選択肢が**着手前実測で不完全と分かった**（`field` の存在）。
  **地図の選択肢は手順書を書く時点で実測し直す**——[DR-0006](DR-0006-shadcn-base-radix-preset-nova.md)（一次情報も古くなる）の 3 例目。

**🟥 推論（未検証）**

- 「**器で済む形を先に探す**」が一般則として機能するかは、**工程6（チャート・ガント）で初めて試される。**
  チャートは器だけで済まない可能性が高い（描画そのものが依存の中身）ので、**そこが規約の強度を測る場所**になる。
- `devDependencies` に置いた rhf / zod は、**使い回し先が「同じ形で編集を組みたい」と言ったときに
  「規約としてどう伝えるか」が未解決**。コードは渡らないので、**規約文書（未決 #7）の材料**になる。

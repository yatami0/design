# DR-0002: 検証対象は画面ではなく 3 層（Tokens / Components / Patterns・Templates）

## 背景

ユーザーの見立て「画面はどうせ変わるが、共通コンポーネントとレイアウトは変わらない」を、検証設計に落とす必要があった。

## 決定

1. **検証対象は [共通コンポーネント思想](../共通コンポーネント思想.md) の 3 層**（① Tokens / ② Components 役割 9 カテゴリ / ③ Patterns・Templates）。画面は対象ではない。
2. **検証スコープは「チケット一覧 1 画面」だが、画面は成果物ではなく部品を洗い出させるための口実**として扱う。
3. 部品の粒度は **① Tokens 全部 + ② Components 9 カテゴリ + ③ Patterns/Templates の骨格**まで（ユーザー決定 2026-07-26）。`@repo/ui` 相当のパッケージ境界は切らない。
4. 「共通部品は変わらない」は**前提ではなく検証対象**として扱う。

## 根拠（実測）

- 「変わりやすさ」ではなく**変更コストの非対称性**が理由。画面が変わるコストは 1 画面ぶん、下の層が変わるコストは全画面。
- PoC 側で**先に立っている構造はすべて下の層を守るもの**だった：`tailwindcss/no-arbitrary-value: 'error'`（`packages/eslint-config/next.js` L84）・`theme.css`（トークン語彙の正本）。一方、画面に対する規約は `ui.md` の「`page.tsx` は薄く」程度しか無い。**守る機構が集中している層＝検証すべき層。**
- 決定4 の根拠は PoC の OBS-0003：「箱を触らずテーマだけ変える」は意味トークン運用＋任意値禁止という**構造的前提の上にだけ**成立する。前提が成り立つかを確かめるのが今回の仕事。

## 影響

- Claude Design の合否判定が変わる。「出力コードが lint を通るか」ではなく、**「登録した共通部品を使うのか、似た見た目を作り直すのか」**が先に来る（`/design-sync` が同期するのはコンポーネントであって画面ではないため）。
- ①は S1 の要求が無くても回せる＝今日から着手できる。

# DR-0086: Redmine は EVM の計画（ベースライン）も進捗の日次履歴も返さない

## 背景

工程2 Q1（★ EVM とガントに必要なデータの形は何か）に答えるため、
Redmine の REST API の一次情報を**逐語で引いて**画面の要求と突き合わせた（[データモデル.md](../データモデル.md)）。
「EVM の画面を作れるか」ではなく「**何が取れて何が取れないか**」を先に確定させるのが目的。

## 発見

**ガントに必要なものは全部ある。EVM は 3 本足りない。**

| | EVM の 3 要素 | Redmine から取れるか |
| --- | --- | --- |
| **PV**（計画価値） | 日付ごとの計画 | 🟥 **無い。**あるのは `start_date` / `due_date` / `estimated_hours` の**現在値**だけ。**計画の凍結（ベースライン）という概念が API に無い**ので、期限を動かすと**過去の PV も一緒に動く**（＝ 計画が実績を追いかけ、スケジュール差異が構造的に 0 へ寄る） |
| **EV**（出来高） | 日付ごとの `done_ratio` | 🟥 **一覧では取れない。**履歴は `journals` にあるが、**`include=journals` は単票専用**——一覧（`GET /issues.json`）の `include` に書けるのは `attachments` と `relations` の **2 つだけ**（公式 wiki の逐語）。60 件の EV 曲線には **60 リクエスト**要る |
| **AC**（実コスト） | 日付ごとの投入 | 🟦 **取れる。**`time_entries` が `spent_on` を持つ唯一の日次データ |

ほかに 2 つ足りない: **単価・金額**（標準に無い＝ EVM は「時間」で回すしかない）と、
**稼働可能時間・非稼働日**（稼働表の「予定」列とガントの日数計算が Redmine 由来では作れない）。

🟦 **逆にガントは揃っていた**——開始 / 期限 / 進捗 / 親子 / `precedes`＋`delay` / マイルストーン（`version.due_date`）。
しかも依存関係は**一覧の `include=relations` で取れる**。
→ **ガントが最重なのはデータではなく描画**であることが、差集合で裏づいた（工程6 Q2 が本体）。

## 根拠（実測）

- 2026-08-07 取得の公式 wiki（Rest_Issues / Rest_TimeEntries / Rest_IssueRelations / Rest_Versions）。
  `include` の許容値は**両端点ぶんを逐語で引用して確認**した（一覧 2 値 ／ 単票 7 値）
- 🟨 TimeEntries は **wiki に応答の全フィールドが載っていない**（POST の引数だけ）。`spent_on` / `hours` は引数として明記
- モック側の実測: 生成した 60 件のうち **open 41 / closed 19**、作業時間 **187 件・404.3 h**（2026-06-01〜08-07）。
  🟥 Redmine の `limit` 上限は **100** なので、**AC の全期間を引くだけでページングが要る**

## 影響

**観測から直接言えること**

- **工程7（EVM）は「描画の工程」ではなく「導出規則を決める工程」になる。**
  PV の按分規則（均等 / 稼働日のみ / 見積の重み）を**誰が決めてどこに置くか**が設計の主題。
- モックは **PV を返さない**（手順書 D10=A）。返すと実 API に無いものを画面が前提にしてしまい、
  繋いだ日に消える。**「モックは実 API が返せるものしか返さない」がこの器の規律。**
- EV の時系列は**取得コストが構造的に高い**（単票 × 件数）。工程7 は
  「曲線を引く」前に「**何リクエストで引くのか**」を決める必要がある。

**🟥 推論（未検証）**

- ベースラインを工場側で持つ（スナップショットを別 resource にする）のは**実装可能だが未検証**。
  やるなら「Redmine の外の概念」であることを画面にも明示する必要がある。判断は工程7。

## 1. 分類の軸 — 8 本の実測

| DS | 部品一覧の分類 | 役割分類はどこにあるか |
| --- | --- | --- |
| shadcn/ui | **アルファベット順**（約 70 件・グルーピング無し） | 無い。registry は**粒度・種別**（ui / component / block / lib / hook…）、blocks は**ユースケース**（dashboard / login…）——場所ごとに軸が違う |
| Radix | **アルファベット順**（30 件） | 無い。唯一の意味的区分は **Components か Utilities か**（Portal / Slot / VisuallyHidden 等の合成道具が別枠） |
| Base UI | **アルファベット順**（44 件・フラット） | 無い |
| Material UI | 🟦 **役割分類あり**: Inputs / Data display / Feedback / Surfaces / Navigation / Layout / Utils / Lab | ★ ただし**カタログ（docs ナビ）にだけ存在**。コードは `export * from './Accordion'` の並列で、**役割別モジュールは無い** |
| Primer | **アルファベット順**（Components 節） | 部品一覧には無い。**上位の文書層**（UI Patterns = "common user workflows" / Scenario Patterns = copy・delete・filter・search）が目的別 |
| Carbon | **アルファベット順**（46 件） | 部品一覧には無い。ナビ階層が **Elements（素材）/ Components / Patterns** を分離し、Patterns（17 種・コード無し）が目的別 |
| Ark UI | **アルファベット順**（70+ 件・フラット） | 無い。🟨 全部品が同種（state machine ＋ anatomy）なので**分類する軸が要らない**——分類軸の不在が「1 責務の層」であることの現れ |
| Chakra v3 | 🟦 **役割分類あり**: Layout / Typography / Buttons / Forms / Collections / Overlays / Disclosure / Feedback / Data Display ほか 11 カテゴリ | ★ **Ark に無い「見た目だけの部品」（Layout・Typography）を足したことで、部品の種類が複数になり分類軸が必要になった**。カテゴリは**下層（Ark）依存の有無とほぼ対応**する |
| Polaris | 🟦 **役割分類あり**: Actions / Layout and structure / Selection and input / Images and icons / Feedback indicators / Typography / Tables / Lists / Navigation / Overlays / Utilities | **役割 9 カテゴリに最も近い形が実在**。ただし「素材↔製品」の層境界はナビに現れず、**props の型（トークン型 props を持つのは Box 系だけ）にだけ現れる** |
| React Aria Components | 🟦 **役割分類あり**（旧 docs・mdx の `category:` が正本）: Buttons / Collections / Color / Date and Time / Drag and drop / Forms / Navigation / Overlays / Pickers / Status | ★ **headless 側で唯一の役割分類**。同じ ListBox でも「一覧＝Collections」「選ぶ入口＝Pickers」に分かれる＝役割で切っている証拠。🟨 2026 の docs 再設計でカテゴリナビは廃止されフラット＋タグへ |
| React Spectrum | 同じ役割カテゴリ | 🟦 **分類の軸は二層で同じまま**。変わるのは合成の開閉だけ（§2） |
| **我々** | **役割 9 カテゴリがディレクトリ**（`src/components/<役割>/`・手3）で、**story の第 1 階層は層**（[DR-0051](DR/DR-0051-storybook-organized-by-layer-with-viewpoint-cards.md)） | **コード構造そのものに役割分類がある**——調査した 8 本のどれとも違う |

★ **Q4 に効く事実 1**: 部品一覧を役割で分類している DS は **Material UI・Chakra・Polaris・React Aria/Spectrum の 4 組**。headless 側は Radix・Base UI・Ark が**アルファベット順**で、**例外は React Aria Components だけ**（役割カテゴリを持つが、2026 の docs 再設計で廃止）。かつ、**役割分類がコード構造（ディレクトリ・モジュール）に現れる DS は 8 本中 0 本**——**分類は「人が探すための索引」であって「コードの構造」ではない**。

★ **Q4 に効く事実 1b（Chakra が示した規則性）**: 分類軸は**部品の種類が複数になったときに生まれる**。Ark（振る舞い部品だけ）は無分類で足り、Chakra（振る舞い部品 ＋ 見た目部品）になった瞬間に役割分類が要る。**役割分類は製品層の性質**であって、素材層には要らない。

★ **Q4 に効く事実 2**: 役割・目的による分類は消えているのではなく、**上へ移動している**——Primer / Carbon はどちらも部品の上の**文書層**（Patterns）が「ユーザーの目的」で切られている。分類の軸は**層によって変わる**（下層: 無分類 → 部品: 索引 → パターン: 目的）。

## 2. 合成の軸 — 全 DS が compound を持つ

| DS | 合成の仕組み | 形 |
| --- | --- | --- |
| shadcn/ui | compound（`Card`+`CardHeader`+…・`data-slot` 属性で部品間連動）＋ `asChild`（Radix 版）/ `render` prop（Base UI 版） | 平置き export |
| Radix | **compound が設計の主軸**（Select は 16 parts）。理由の明文: "granular access to each component part, so you can wrap them"。＋ `asChild`（Slot） | Root/Trigger/Content… |
| Base UI | compound（namespace parts: `Popover.Root > .Trigger > .Positioner > .Popup`）＋ `render` prop ＋ `className(state)` 関数 | namespace |
| Material UI | **単一部品 ＋ props**。内部到達は `slots` / `slotProps`（"A component's structure is determined by the elements that fill that component's slots"） | 単一 |
| Primer | compound（`Object.assign(List, {Item, Group, …})` → `ActionList.Item` 形式）＋ 自前 slot 機構 | Object.assign |
| Carbon | compound（`Tabs/TabList/TabPanel`・`DataTable/TableHead/…`）＋ `as` prop（polymorphic） | 平置き export |
| Ark ↔ Chakra | **両層とも compound ＋ `asChild`**。Chakra は Ark の各 part を slot recipe の slot に 1:1 で結線して包み直す（**閉じた 1 枚部品には畳まない**）。閉じた形が欲しい利用者には **snippet**（CLI がソースを利用者のツリーに複製） | namespace ＋ 複製 |
| React Aria ↔ Spectrum | ★ **非対称が最も明瞭**: RAC は open compound ＋ context（親が context に流し、汎用の子部品が拾う）／ Spectrum は**閉じた単一部品 ＋ props**（`<Picker label="…">`——label もエラーも props。トリガーも Popover も外から見えない）。🟨 ただし全面ではない——**フィールドの解剖（label・エラー・中身）は閉じるが、トリガーと中身の結合（`MenuTrigger`）は上層でも合成のまま** | 開閉が層で反転 |
| **我々** | 素材層は shadcn の compound をそのまま再輸出。**自作 9 件は単一部品 ＋ union props**（`DataGrid`・`StatusPill`・Layout 7 件）。`asChild` は持たない | 単一 |

🟨 **観測**: headless 側（Radix・Base UI・Ark・RAC）は **compound が太く**、styled・製品側（Material UI・Spectrum・我々の自作）は**単一部品 ＋ props に圧縮**される。Radix の Custom APIs 節（"Create your own API by abstracting the primitive parts"）は**この圧縮こそが上層の仕事**だと言っている。React Aria↔Spectrum が最も鮮明——**分類の軸は二層で同じまま、合成の開閉だけが層の境界で反転する**（同じ「Pickers」カテゴリが、下層では「素材をどう組むかのパターン名」、上層では「完成品の棚の名前」として機能する）。**合成の開閉が層の実体で、分類は層をまたいで安定な索引**。

## 3. 仮説の検証 — 「分類の軸」と「合成の軸」は別物か

**別物だった。**8 本とも:

1. **分類**は docs ナビ・registry・パターン集という**人間向けの索引**に住む（Material UI の役割分類がコードに無いのが決定的）
2. **合成**は Root/Trigger/parts・slots・asChild という**ランタイム API** に住む
3. 両者を繋ぐ規則（「この分類の部品はこう合成する」）は**どの DS にも見つからなかった**（shadcn の "common, composable interface" が最接近だが、分類とは接続されていない）

🟨 Radix はこの分離の極端な形——**分類はほぼ退化し（アルファベット順）、設計の実体は合成**（compound + Slot）にある。分類が痩せているのは欠落ではなく、**合成が太いことの帰結**（調査エージェントの分析・🟥 推測マーク付きで受領）。

★ ユーザーの見立て「素材層を組み合わせるための**抽象的な**製品層」に照らすと: 各 DS で「抽象化」が住んでいるのは**分類ではなく合成**だった。役割 9 カテゴリ（分類）は部品を**探す**軸としては機能するが、**作る**部品を決める軸としては、どの DS も使っていない。

## 4. 我々の役割 9 カテゴリの位置（Q4・Q7 の観測）

- **役割 9 カテゴリと同じ軸**（Inputs / Data display / Feedback…）は Material UI・Polaris・React Aria/Spectrum のカタログに実在する——**分類として特殊ではない**。とくに Polaris の 11 カテゴリは我々の 9 カテゴリとほぼ重なる
- ただし**分類をコードのディレクトリにまで下ろしている**のは我々だけ（8 本中 0 本）。手6 で観測した「層と役割が `group` 1 本に潰れる」（[指摘 9](共通コンポーネント思想への指摘.md)）は、**分類が複数軸あるのに器が 1 本**という我々固有の問題ではなく、**分類を索引以上のものとして運ぶこと自体が例外**という位置づけになる
- 🟨 **指摘 12 件目（→ [指摘集](共通コンポーネント思想への指摘.md) に起票済み）**: 思想の役割 9 カテゴリは「**探す軸**」としては外の DS と整合する。だが「**何を作るか・どう合成するか**」を決める軸は思想に無く、調査した DS では**合成の仕組み**（compound / 単一 + props / slot）と**上の文書層**（Patterns = 目的）が担っている。**思想は分類表であって合成規則を持たない**——手8c の設計（何を作るか）が思想から直接導けないのは、このため

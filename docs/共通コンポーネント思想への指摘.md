## 1. 「部品でないもの」の置き場が無い

**思想の記述**: 役割 9 カテゴリは「Action / TextInput / … / Display」で、いずれも**画面に出るもの**。

**実装で起きたこと**: `Direction`（RTL/LTR をツリーに配るコンテキスト提供者）が**どのカテゴリにも入らなかった**（手1・[部品カタログ 表2](部品カタログ.md)）。
手2b では `TooltipProvider` と `SidebarProvider` が**実装でも配線を要求した**。手4 では `AppProviders` として実体になった。

**なぜ起きるか**: 分類の軸が「**画面上の役割**」なので、**画面に出ないもの**は原理的に入らない。
無理に入れると「Provider は Display か？」のような答えの無い問いが生まれる。

**提案**: 分類表に足すのではなく、**分類の外に「配線（wiring）」という置き場がある**と明記する。
> 実装では製品層の直下（`src/components/providers.tsx`）に置いた。**Provider は部品ではなく、部品が動くための前提条件**（DR-0037）。

## 2. Overlay の定義が 2 条件の AND になっている

**思想の記述**: `Overlay（重なり・開閉）`。

**実装で起きたこと**: `Accordion` と `Collapsible` が**どちらにも入らなかった**。
**開閉するが重ならない**ので Overlay ではなく、かといって Layout（Box / Stack / Grid / Container / Spacer / Card / Section）でもない。

**なぜ起きるか**: 「重なり」**かつ**「開閉」の 2 条件を AND で定義しているため、
**片方だけを満たす部品**（disclosure 系）の居場所が無い。

**提案**: **Overlay は「重なり」だけで定義し、開閉は `stateful` フラグで表す。**
思想自身が「状態を分類軸にせず、hook とフラグで表す」と決めているので、**その趣旨と一貫する。**

🟨 **未検証**: Accordion / Collapsible は導入していないので、実装では顕在化していない。

## 3. フラグに `provider` が要る（種類は 2 つある）

**思想の記述**: フラグは `stateful` / `behaviorHook` / `formBound` / `overlay` / `container` の 5 つ。

**実装で起きたこと**: `TooltipProvider` は **hook ではなく Provider で配線する**ので `behaviorHook` では表せない（手1）。
🆕 **手4 で、Provider には 2 種類あることが分かった**（[DR-0031](DR/DR-0031-sidebar-red-is-not-state.md)）。

| 部品 | 要求するもの | 種類 |
|---|---|---|
| `tooltip.tsx` | `TooltipProvider` | 🟦 **設定の配布**（`delayDuration` 等）。状態を持たない |
| `sidebar.tsx` | `SidebarProvider` | 🟨 **状態の配布** |

**提案**: `provider` フラグを足すなら、**値を `'config' | 'state'` の 2 種にする**。
🟨 🆕 **2026-08-07: 保留の理由を差し替えた**（[DR-0077](DR/DR-0077-abolish-the-two-occurrence-rule.md) で 2 回ルールを廃止）。
~~必要性が 1 度しか証明されていない~~ ではなく、**Provider を要求する部品が 18 件中 2 件しかなく、フラグを足しても分類が変わる部品が 2 件しかない**（＝**分類表としての情報量が増えない**）が理由。🟥 **これは思想の持ち主（ユーザー）の判断で、いつ足してもよい。**

## 4. 「不可侵」に適用範囲が書かれていない

**思想の記述**（継承元の `apple.md` §4.5「[公式・不可侵]」）: 「タッチターゲット **44×44px 以上**」。

**実装で起きたこと**: 本 repo は当初これを「**全コントロールの下限**」と読み、
shadcn nova の `h-8`(32px) を「不可侵の下限を割っている」と記録した（[DR-0023](DR/DR-0023-real-conflict-is-touch-target.md)）。
**一次情報を辿ると、tmp-admin が実際に適用しているのは `nav-item` の `min-height` 1 箇所だけ**だった（[DR-0030](DR/DR-0030-touch-target-provenance-corrected.md)）。

**なぜ起きるか**: 「44×44px 以上」とだけ書かれ、**何に適用するか**（全コントロールか／タッチ操作するものだけか／nav-item だけか）が規定されていない。
**値の話と範囲の話が分離されていない。**

**提案**: 「不可侵」を**値に対する宣言**と読み、**範囲は各 variant / 各プロジェクトが決める**と明記する。
> 実装ではさらに「**当たり判定に対する要求**」と読み替え、見た目 32px と両立させた（DR-0034）。
> Apple 自身が「タップできる面積であって見た目ではない」と定義しているので、この読み替えには根拠がある。

## 5. 「状態は hook へ」が状態と副作用を区別していない

**思想の記述**: 「状態は role の外に出し、開閉は `useXxxModal()` / `useXxxDrawer()` へ、入力値は RHF + Zod へ切り出す」。

**実装で起きたこと**: shadcn の `Sidebar` を調べると、**抱えていたのは「状態 1 つ」ではなく「関心事 4 つ」**だった。

| # | 関心事 | 種類 | 思想の射程 |
|---|---|---|---|
| 1 | 開閉状態（`useState` + 制御 props） | **状態** | 🟦 射程内 |
| 2 | 永続化（`document.cookie` に 7 日） | **副作用** | 🟥 射程外 |
| 3 | グローバルショートカット（`window` に Cmd/Ctrl+B） | **副作用** | 🟥 射程外 |
| 4 | レスポンシブ分岐（`useIsMobile` で Sheet に差し替え） | **方針** | 🟥 射程外 |

**なぜ起きるか**: 「状態を外に出す」だけでは、**副作用（永続化・グローバルキーバインド）と方針（レスポンシブ）の置き場が決まらない**。
`stateful` フラグも同じで、「状態を持つ」とだけ記録しても**何を持っているかが分からない**。

**提案**: 「状態」を **状態 / 副作用 / 方針**の 3 つに割ってから置き場を決める。
🟨 フラグを増やすなら `sideEffect` / `globalKeybinding` の軸が要るかもしれないが、**必要性はまだ 1 回**。

## 6. Layout の欠落リストに `Inline` が無い

**思想の記述**: Layout カテゴリは `Box, Stack, Grid, Container, Spacer, Card, Section`。

**実装で起きたこと**: Layout プリミティブを書いたとき、**`Stack`（縦積み）だけでは横並びが組めなかった**。
一覧の見出し行（件数 + 主要操作）を組むのに 7 件目として `Inline` が必要になった（手3）。

**なぜ起きるか**: `Stack` を「縦積み」と定義した時点で、**横方向の対が要る**。
Braid / Chakra / Grafana など実在の設計システムはいずれも `Stack` と `Inline`（または `HStack`）を対で持っている。

**提案**: Layout カテゴリに **`Inline`** を足す。**代替として `Stack` に `direction` prop を持たせる案もある**が、
「縦積み」という名前と食い違うので、別部品にするほうが名前と実体が一致する。

## 7. ③ 層は一枚岩ではない ★手4 の発見

**思想の記述**: 「コンポーネントの足し算だけではページにならない。**組み合わせの定石はひとつ上の層になる**」。

**実装で起きたこと**: 先に仮説として 3 件を切り出してから画面を組んだところ、**1 件は足し算で書けた**。

| 切り出したもの | 足し算で出るか | 持っていたもの |
|---|---|---|
| `ListDetail`（一覧 + 詳細シート） | 🟦 **出ない** | 状態の調整（`useListDetail`）＋ DataDisplay × Overlay の突き合わせ |
| `AppShell`（ページ骨格） | 🟨 微妙 | 構造は足し算だが「3 層の面の割り当て」は部品に書けない |
| `EmptyState`（空状態） | 🟥 **出る** | 素材の `Empty` を薄く包んだ 12 行 |

**なぜ起きるか**: 「足し算で出ない」は **③ 層全体の性質ではなく、③ 層に置くための条件**だった。
実装して分かった条件は 2 つで、**少なくとも一方を満たすものだけが ③ 層に属する。**

1. **状態を持つ**
2. **複数の役割カテゴリをまたぐ**

**提案**: 思想③に**置くための条件**を明記する。条件を満たさないものは ② 層のラッパーで足りる。

## 8. トークンは「値」を分類するが「値の作り方」を分類しない ★手5 の発見

**思想の記述**（① 層）: 3 層トークン（primitive / semantic / component）と、
「**UI はこれ（semantic）だけを使う**」「**数値直書きの禁止は lint で検知できるはず**」。

**実装で起きたこと**: 手5 でトークンを差し替えたところ、
**素材層の 17 種 60 箇所が、色は追従したのに濃さだけ動かなかった**（[DR-0045](DR/DR-0045-opacity-modifiers-were-invisible-to-lint.md)）。

```
bg-destructive/10   →  color-mix(in oklab, var(--destructive) 10%, transparent)
                        └─ トークン ────┘  └─ トークンではない ─┘
```

**`10` はクラス名に住んでいて、primitive でも semantic でも component でもない。**

**なぜ起きるか**: 3 層は**値の抽象度**で切った分類なので、
「**値をどう合成するか**」という軸を持たない。ところが状態面の作り方は**流派が 2 つある**。

| 流派 | 作り方 | トークンに載るもの | 手5 で起きたこと |
| --- | --- | --- | --- |
| shadcn | **合成する**（意味色 × 不透明度・3 段） | 色だけ。係数はクラス名 | 🟥 **色は追従・濃さは固定** |
| tmp-admin V4 | **合成しない**（合成済みの結果を専用トークンに） | `--fill-danger: rgba(255,59,48,.16)` | 🟦 丸ごと追従 |

**どちらも「semantic だけを使う」を守っている。**それでも**片方は枠が閉じ、片方は閉じない。**
→ 「semantic だけを使う」は**枠が閉じることの十分条件ではない。**

🟥 **併記されている「lint で検知できるはず」も、この形には効かない。**
`/10` は任意値（`[...]`）ではなく正規の Tailwind 構文なので、任意値禁止 lint は赤くしない。
**「トークン化されていない値」の集合は lint の赤では取れない**（[DR-0045](DR/DR-0045-opacity-modifiers-were-invisible-to-lint.md)）。

🟨 **同じ機構がリングにも出る。**`ring-destructive/20` と `ring-ring/50` は
**同じ `--tw-ring-color` を奪い合う**ので、エラー中の入力欄はフォーカスしても見た目が変わらない
（[DR-0054](DR/DR-0054-mock-specimens-cannot-reproduce-stacked-states.md)）。**合成の係数がトークンの外にある限り、この衝突は設計できない。**

**提案**: ① 層に**「合成をトークンの内側でやるか、外側でやるか」を決める**という項を足す。

- **内側**（tmp-admin 方式）＝ 状態面ごとに semantic トークンを持つ。**枠は閉じるが語彙が増える**
- **外側**（shadcn 方式）＝ 色トークン + 修飾子。**語彙は少ないが枠は閉じない**

🟥 **本 repo はまだ選んでいない。**概念の理解ごと [OBS-0009](OBS/OBS-0009_不透明度と状態面の概念を理解する.md) に積んである。

## 9. 分類の軸が 3 本あるのに、渡し先の器は 1 本しか持てない ★手6 の発見

**思想の記述**: 分類は 3 本の軸で立っている。

| 軸 | 思想での役割 |
| --- | --- |
| **① / ② / ③ の 3 層** | 抽象度（値 → 部品 → 組み合わせ） |
| **役割 9 カテゴリ**（② の中） | 「何をする部品か」。**主キー** |
| **フラグ 5 種** | 絞り込み軸。「**AI が『どの部品を使うべきか』を辞書引きできるようにする**」 |

**実装で起きたこと**: 手6 で Claude Design へ渡したとき、**3 本とも同じ形では渡らなかった。**

### 9.1 層と役割が 1 本の軸に潰れた

渡し先が持つ分類は `group` **1 本だけ**。Storybook は 2 階層あるので
層（第 1 階層）と役割（第 2 階層）を両方表現できていたが（[DR-0051](DR/DR-0051-storybook-organized-by-layer-with-viewpoint-cards.md)）、
`group` に落ちるのは**タイトルの 1 つ手前のセグメント 1 個**だけだった。結果、出荷された 6 グループは**種類が混ざった**。

| 出荷された `group` | 実体 |
| --- | --- |
| `action` / `datadisplay` / `layout` / `navigation` | 🟦 **役割**（② の中のカテゴリ） |
| `patterns` / `templates` | 🟥 **層**（③ / ④） |

**design agent から見ると `layout` と `patterns` は兄弟に見えるが、片方は役割で片方は層。**
これは変換の事故ではなく、**2 本の軸を 1 本に射影した以上どちらかが混ざる**という構造的な帰結。

### 9.2 フラグは「絞り込み軸」としては渡らなかった

思想はフラグの目的を「**AI が辞書引きできるようにする**」（ファセット分類・Amazon の絞り込みフィルタ）と書いている。
ところが**渡し先の AI が受け取るのは散文**だった——conventions header は
**design agent の system prompt に inline される文章**で、**クエリを投げる口は無い。**

skill 自身がこう書いている:

> agent は**列挙された具体的な指示にしか従えない**。語彙を名指ししなければ、agent は推測しない——**自分のものを発明する**。

→ **フラグを facet のまま渡す先が無かった**ので、手6 では**手で散文に翻訳した**。

```
思想:  stateful / behaviorHook / container …（属性）
実装:  「owns state / needs a provider — Sidebar と AppShell は SidebarProvider に
        開閉状態を持つので AppProviders が必須。ListDetail は useListDetail() を呼んで
        state に渡す」（文章）
```

🟨 **翻訳できたので実害は出ていない。**ただし**属性は機械が畳めるが、散文は畳めない。**
部品が増えたとき、この翻訳は人が書き足し続けることになる。

**提案**: フラグの節に「**渡し先が facet 検索を持たないとき、フラグは散文に翻訳される**」という前提を書き、
**翻訳しても意味が落ちない粒度**でフラグを定義する（例: `stateful` 単体ではなく
「どの Provider が要るか」まで書ける形にする）。9.1 については、**層と役割のどちらを優先して渡すかを決めておく。**

🟥 **推論（未検証）**: 「散文に翻訳したフラグが design agent に効くか」は**手7 で初めて分かる。**
効かなければ、思想の「AI が辞書引きできるように」という目的自体が、
**この渡し先では別の手段（`.prompt.md` の充実など）に置き換わることになる。**

## 10. 「枠を props で閉じる」は層ごとに成否が違うのに、思想はそれを層の属性として書いていない ★手7 の発見

**思想は 3 層（① Tokens / ② Components / ③ Patterns・Templates）を分けているが、
「枠がどこまで閉じるか」は層の属性として規定されていない。実装するとここが割れる。**

| 層 | `className` を受けるか | 枠は閉じるか |
| --- | --- | --- |
| ② 製品層・自作（Layout 7 件） | 🟦 **受けない**（`Box` だけが逃げ道） | 🟦 **閉じる**（[DR-0032](DR/DR-0032-layout-primitives-take-props-not-classname.md)） |
| ② 製品層・ラッパー（`Button` / `Sidebar`） | 🟨 受ける（素材層の面をそのまま持ち上げる） | 🟨 部分的 |
| 🟥 **② 素材層 16 件** | 🟥 **受ける。しかも寸法の props を 1 つも持たない** | 🟥 **開いている** |

### 10.1 実測 — 逸脱は素材層にだけ付いた

手7 で Claude Design に 3 周組ませた結果、**任意のクラスが付いたのは素材層の部品だけ**だった。

| 周 | 逸脱 | 付いた場所 |
| --- | --- | --- |
| 2 周目 | `class-name="w-48"` × 2 | 🟥 **`SelectTrigger`（素材層）** |
| 1・2・3 周目 | — | 🟦 **製品層の部品には 1 つも付いていない** |

`.d.ts` を見ると、素材層に**寸法系の props は 1 つも無い**（`Select` はゼロ、`Input` / `Table` は `className?` のみ）。
**幅を決める手段が `className` しか無い。**

### 10.2 ただし「props を生やす」では解けなかった

🟥 **根因は props の不在ではなく、語彙の不在だった**（[DR-0060](DR/DR-0060-vocabulary-leaks-from-four-surfaces.md)）。
思想の ① Tokens 層に「**コントロール 1 個分の横幅**」を表す語が無く、
`--container-content` / `--container-wide`（ページ幅）しか無かった。
→ 幅の語彙を足したら **3 周目で `w-field-md` が使われ、逸脱が消えた**（[DR-0063](DR/DR-0063-forbidding-without-an-alternative-fails.md)）。

**仮に素材層に `width` prop を生やしても、渡す値の語彙が無いので同じことが起きていた。**

### 10.3 指摘の中身

1. 🟥 **「枠は props で閉じる」を層の属性として書く必要がある。**
   いまの思想では「Layout プリミティブは…」という**部品単位**の話になっており、
   **素材層は枠の外にある**ことが読み取れない。
2. 🟥 **① Tokens 層の語彙に「用途の粒度」が規定されていない。**
   ページ幅は定義され、コントロール幅は定義されていなかった。
   **どの粒度まで語彙を持つかの基準が無い**ため、欠落が使ってみるまで分からない。
3. 🟨 **逸脱の面は 4 つあり、層の話で塞がるのは 1 つだけ**（[DR-0060](DR/DR-0060-vocabulary-leaks-from-four-surfaces.md)）。
   `DataGrid.columns[].cell` のように **props が ReactNode / 関数を受ける箇所は、どの層でも枠の外**になる。
   思想はこの「**API の形が作る穴**」を扱っていない。


## 11. 「定義したものだけを使う」は許可リストだが、機械の網は禁止リストしかない ★手8 の発見

### 11.1 実測 — `tabular-nums` はどの網にも掛からない

思想と conventions header は「**定義した語彙だけを使う**」と書いている。これは**許可リスト**の言い方。
ところが、境界の両側にある機械の網は**どちらも禁止リスト**だった。

| 網 | 何を列挙しているか | `tabular-nums` を捕まえるか |
| --- | --- | --- |
| 我々の `no-restricted-syntax` | **数値の段**と**パレット色**の正規表現 | 🟥 **捕まえない**（どちらにも当たらない） |
| 我々の `tailwindcss/no-arbitrary-value` | **角括弧** | 🟥 捕まえない |
| 受け手の `no-restricted-syntax` | **生 hex** と **`\d+px`** | 🟥 捕まえない（そもそも className を見ない） |
| 受け手の `react/forbid-elements` | **素の HTML 要素** | 🟥 捕まえない |

🟦 **`tabular-nums` は CSS に実在する。**Tailwind の正規のユーティリティで、`_ds_bundle.css` にも載っている。
🟥 **実在するが、宣言語彙の外にある**——**「存在すること」と「使ってよいこと」がずれている。**

### 11.2 禁止リストでは原理的に閉じない

[DR-0063](DR/DR-0063-forbidding-without-an-alternative-fails.md) は「**禁止だけでは破られ、代替語彙を与えると守られた**」と結論した。
🟥 **手8 はその一段先を見せた**——**代替を与えても、許可リストを閉じない限り「宣言していない実在クラス」は残る。**

- 禁止リストは**列挙したものしか止められない**。Tailwind のユーティリティは数千あり、**列挙しきれない**
- 実際、逸脱は 5 → 2 → **1** まで減ったが、
  **最後の 1 が消えないのは「代替が無い」からではなく「列挙されていない」から**
- 🟨 **1 まで減ったのは散文の規約が効いたから**であって、**機械が止めたからではない**（[DR-0066](DR/DR-0066-neither-side-lints-the-generated-output.md)）

### 11.3 指摘の中身

1. 🟥 **思想は語彙を「許可リスト」として定義しているのに、それを強制する手段を書いていない。**
   ① Tokens 層は「これが語彙です」と列挙するが、**「列挙外は使えない」を機械で言う方法**が無い。
2. 🟥 **「トークンの語彙」と「使ってよいクラスの語彙」が同じものとして扱われている。**
   実際には**トークンから生成されるクラス**（`w-field-md`）と**トークンと無関係に存在するクラス**（`tabular-nums`）があり、
   **後者は語彙表に載らないまま使える。**
3. 🟨 **許可リストを機械化するなら検査の形が変わる**——「禁止語を列挙する」から
   「**className に現れた全トークンを語彙表と突き合わせる**」へ。
   🟥 **これは本 repo にも PoC にも存在しない検査。**
   🆕 **2026-08-07: 「1 回目だから保留」は理由でなくなった**（[DR-0077](DR/DR-0077-abolish-the-two-occurrence-rule.md)）。
   **作るかどうかは中身で判断してよい**——🟦 実装例は実在する（[DR-0071](DR/DR-0071-closed-product-layer-is-viable.md)・Spectrum S2 の style macro）。
   🟥 **残る障害は「受け手側の lint 規則は `.d.ts` から自動生成されるので、こちらから検査を足せない」**（[DR-0059](DR/DR-0059-receiver-generates-its-own-adherence-lint.md)）——**これは回数と無関係に効く制約。**

## 12. 思想は分類表であって、合成の規則を持たない ★手8c の発見

**思想の役割 9 カテゴリは「部品を探す軸」としては外の DS と整合する**——手8c で DS 8 本と突き合わせたところ、
同じ役割分類が Material UI・Polaris（11 カテゴリ・我々とほぼ重なる）・React Aria/Spectrum のカタログに実在した
（[製品層の抽象化の軸.md](製品層の抽象化の軸.md)）。**分類として特殊ではない。**

問題は用途の方にある。**手8c の問い「製品層に何を作るべきか」に、思想は答えを持っていなかった:**

- 8 本の DS で、役割分類が**コード構造（何を作るか・どう組むか）を決めている例は 0 本**——分類は**人が探すための索引**
- 「何を作るか」を決めているのは**合成の仕組み**（compound ／ 単一部品 + props ／ slot）と、
  部品の上の**目的の層**（Primer / Carbon の Patterns = ユーザーの目的で切った文書層）
- 我々も実際、判定規則（[DR-0070](DR/DR-0070-product-layer-boundary-rule.md): 見た目の管轄権 ＋ 実測回数 ＋ 語彙で表せるか）を
  **思想の外に**立てる必要があった。思想のどのカテゴリに属するかは、作るかどうかの判定に**一度も使われていない**

🟨 **これは指摘 9（分類の軸が 3 本）・指摘 10（枠の閉じ方は層の属性）の続きで、より根が深い**——
分類の**書き方**ではなく、**分類表という形式が「探す」以外の用途を持たない**という話。
思想に「合成の規則」（部品を足す・組む・閉じるの判定）という**別の章**が要るのか、
それとも判定規則は思想の外（DR / ADR）に置き続けるのか——**ユーザー判断**（D5=A により起票のみ。思想は触っていない）。

## 13. 層タグは部品単位でしか付けられないのに、昇格はパーツ単位で起きる ★手8d の発見

思想の 3 層（① Tokens ／ ② Components ／ ③ Patterns・Templates）と、我々が手3 で足した層タグ
（`vendor` ／ `wrapped` ／ `own`）は、**1 部品 = 1 つの層**を前提にしている。
Storybook の棚（[DR-0051](DR/DR-0051-storybook-organized-by-layer-with-viewpoint-cards.md)）も story 1 本 = 棚 1 箇所で並ぶ。

**手8d で、その前提が崩れた。**`Select` は 10 個のパーツ（`Select` / `SelectTrigger` / `SelectContent` /
`SelectItem` / …）を持つ複合部品で、**そのうち `SelectTrigger` だけが製品層のラッパーに昇格した**
（6/6 周の逸脱が全部このパーツから出ていたため。[製品層の部品設計 §3.1](製品層の部品設計.md)）。

- **`vendor` のままにすると嘘**——`SelectTrigger` は `className` を型から消し、幅を製品層が決めている
- **`wrapped` にしても嘘**——残る 9 パーツは素材そのままで、`className` も開いている
- → **タグを 2 つ付けた**（手8d D12=(c)）。棚の位置は素材層のまま（`group` は役割フォルダ由来なので変わらない）

🟥 **これは「分類が粗い」という話ではなく、粒度が 1 段足りないという話。**
判定規則（[DR-0070](DR/DR-0070-product-layer-boundary-rule.md)）は**逸脱が出た場所**で境界を引くので、
**引かれる線は部品の外周とは限らない**——複合部品の内側を通る。
規則が正しく働くほど、**層は部品より細かい単位に付く**ことになる。

🟨 **指摘 10（枠の閉じ方は層ごとに違う）の続き。**10 は「層によって閉じ方が違う」だったが、
13 は「**同じ部品の中で層が分かれる**」。分類の書き方ではなく、**分類が付く単位**の話。

🟨 選択肢はユーザー判断（D5=A により起票のみ・思想は触っていない）:
① タグの複数付けを正式に認める ② パーツ単位の分類を思想に足す
③ 昇格したら**部品ごと製品層へ移す**（＝残り 9 パーツもラッパーにする。🟥 **0/6 周の予防的ラッパー**になる）

## 14. 役割 9 カテゴリに席が無い部品が、1 工程で 3 件出た ★工程4 の発見

思想の役割 9 カテゴリは**フラット・入れ子なし**で、**「探す軸」として維持する**と決めてある
（[製品層の部品設計 §8-5](製品層の部品設計.md)）。工程3 まではこれで足りていた——
Tabs・Breadcrumb・DatePicker は**思想に予約済み**で、「分類の発明は不要」だった。

**工程4（詳細＋編集）で、1 工程のうちに 3 件が席を失った。**

| 部品 | 何をするもの | 9 カテゴリの該当 |
| --- | --- | --- |
| `Field` | フォーム 1 枠の器（ラベル・説明・エラーの置き場） | 🟥 **無い**（TextInput は `TextField, Textarea`・Layout は自作テンプレ 7 種） |
| `DescriptionList` | 項目名と値の対の並び | 🟥 **無い**（DataDisplay は `Table, DataGrid, List（データ）, Tree, Tag, Statistic, Chart`） |
| `Timeline` | 出来事の縦の連なり | 🟥 **無い**（同上） |

**置き場は決めた**（🟥 **思想は書き換えていない**——ユーザーの持ち物なので指摘に留める）:

- `DescriptionList` / `Timeline` → **DataDisplay**。
  根拠は**由来の一次情報**——思想は DataDisplay を「Ant / Carbon の Data Display」由来と書いており、
  **Ant Design は両方とも `group: Data Display` に置いている**（実測: 実行記録 §工程4 P4-05）。
- `Field` → **Layout**。根拠は**先例**——`Card` は shadcn 由来で既に Layout に居る
  （＝ Layout は「自作テンプレ」だけの棚ではない）。

### ★ ここで指摘 12 が具体例を得た

[指摘 12](#12-思想は分類表であってー合成の規則を持たない-手8c-の発見)（思想は分類表であって合成の規則を持たない）が、
**この工程で実害の形になった。**

- **思想は Pattern として「フォームレイアウト」を持っている**（③ 層の例に明記）。
- **なのに、部品としての `Field` の席が無い。**
- そして **`src/patterns/**` は `@/components/ui/*` を import できない**（我々が機械化した層の規則）。
- → **思想の分類どおりに置こうとすると、機械化した規則に阻まれる。**
  製品層に窓口を作るしかなく、**その窓口をどのカテゴリに置くかを思想が答えない。**

🟥 **分類表と合成の規則が別々に育つと、こういう詰まり方をする。**
指摘 12 は手8c 時点では「調査した DS 8 本のうち役割分類がコード構造を決めるものは 0 本」という
**外形の話**だったが、ここでは**自分の repo の中で分類と構造が食い違った**。

🟨 選択肢はユーザー判断（起票のみ・思想は触っていない）:
① カテゴリを足す（`Form` / `Feedback` など） ② DataDisplay / Layout の「含む部品」欄に追記する
③ **カテゴリは「探す軸」なので、置き場の判断は毎回 DR に書く**と決める（＝現状の運用を明文化する）

🟨 **[未決 #25](handoff.md)（指摘の偏りは「規定の細かさ」か「使い込みの量」か）の材料が増えた。**
工程4 は **② 層を初めて「編集」の用途で使った工程**で、そこから 3 件まとめて出た。
🟥 **1 工程で 3 件は初めて**（手4・手5・手6 は 1 手 1 件、手8d も 1 件）——**「使い込みの量」に寄る観測がまた 1 つ。**

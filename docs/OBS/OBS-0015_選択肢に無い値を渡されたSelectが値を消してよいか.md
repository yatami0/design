# OBS-0015: 選択肢に無い値を渡された `Select` が、値を消してよいか

## 0. 何が起きたか（実測・工程4 K1-b）

**Radix の `Select` は、`value` に一致する `SelectItem` が 1 つも無いと `onValueChange("")` を発火する。**

工程4 の詳細画面では、課題（`fetchIssue`）と選択肢（`fetchIssueStatuses`）が**別々に飛ぶ**。
選択肢が届く前に react-hook-form の `reset` が走ると、その瞬間 `SelectItem` は 0 個なので:

```
[dbg] reset with {…,"statusId":6,"priorityId":3,…}   ← rhf には正しく入っている
[dbg] status onValueChange ""                        ← 🟥 Radix が空文字を発火
[dbg] before {"s":6,"p":3} after {"s":0,"p":0}        ← Number('') = 0 に化けた
[msw] PUT /issues/1001.json {"subject":"…","status_id":0,"priority_id":0}
```

🟥 **そして誰も気づけない形で終わっていた**——`status_id: 0` はモックの表に無いので
**ハンドラは黙って何もせず 204 を返し、画面は「保存した」と表示した。**
実 Redmine なら 422 か不正な書き換えになる。

## 1. なぜ疑問なのか

**塞ぎ方を画面側に置いた**（工程4 D16=A・① 選択肢が揃うまでフォームを出さない ② 空文字を無視する）。
**動いている。**が、これは**この画面が覚えていた対処**であって、**規約ではない。**

[DR-0089](../DR/DR-0089-overlays-do-not-cover-their-anchor.md) は同じ種類の問題——
「上流の既定が UI として望ましくない」——を**製品層で固定し、prop にしない**という形で解いた。
**この件も同じ形にできるのではないか。**

## 2. 決まっていないこと

- **コアの `Select` が空文字を飲み込むべきか。**
  🟥 **飲み込むと「選択を消す」用途が塞がる**（クリア可能な Select の需要は、この repo にはまだ 0 件）。
- **あるいは「選択肢が空のあいだは値を保持する」だけで足りるか**（空文字の発火は上流の実装詳細で、
  こちらが見たいのは「値を勝手に消すな」の 1 点）。
- **同じ形が `DropdownMenu` / `Popover` / `Tooltip` にもあるか**は測っていない
  （[DR-0089](../DR/DR-0089-overlays-do-not-cover-their-anchor.md) が残した宿題 ② と同じ未測定）。

## 3. 知識の結びつき

🟥 要確認。以下は仮説:

- **「対象 0 件で緑」の親戚に見える。**prop も型も lint も build も緑で、**作用だけが違っていた**——
  [DR-0090](../DR/DR-0090-token-classes-were-silently-dropped-by-tailwind-merge.md)（`width` prop が一度も効いていなかった）と同じ手触り。
  🟦 **ただし今回は赤テスト（K1-b）が先に置いてあったので、その場で捕まった。**
  **違いは「効果を測る検体を先に書いたかどうか」**だけかもしれない。
- **非同期の到着順が UI の値を壊す**という形は、工程5（稼働表）・工程7（EVM）でも出る余地がある
  （どちらも「選択肢が後から届く」構造を持つ）。

## 4. どう決めるか

**需要を見てから。**判定材料になるのは:

1. 工程5〜8 で**同じ形（選択肢が後から届く Select）が再び出るか**
2. **クリア可能な Select の需要が出るか**（出たら「空文字を飲む」は採れない）

🟨 どちらも回数の話に見えるが、**回数を条件にしているのではない**（[DR-0077](../DR/DR-0077-abolish-the-two-occurrence-rule.md)）——
**「コアが飲み込んでよいか」は、飲み込んで困る用途があるかで決まる**ので、その用途の有無を待っている。

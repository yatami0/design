# OBS-0016: header が名指ししていない出荷部品 8 件を、DR-0069 を踏まずにどう埋めるか

> 凡例：🟦 確定／根拠あり ・ 🟨 暫定／裁量 ・ 🟥 未確認・要本人確認

## 0. 一行サマリ【起票時必須】

2026-08-09 の再同期で、**カードは出荷しているのに `conventions.md` が一度も名指ししていない部品が 8 件**あると分かった
（`DescriptionList` `Timeline` `Breadcrumb` `Tabs` `FilterBar` `FormLayout` `PageHeader` `PeriodSelect`）。
header は「2 層とも実在する部品だから自分で markup を書くな」と言っているので、
**載っていない部品は design agent が手組みする側に回る**——[OBS-0013](OBS-0013_部品があるのにインラインスタイルで組んだ.md) と同じ形。
🟥 **ただし単純に足せない。**[DR-0069](../DR/DR-0069-adding-prohibitions-to-the-header-degraded-the-output.md) で
**842 バイト足したら「触っていない箇所」が壊れた**実績があるため、**埋め方そのものが問い。**

## 1. きっかけ（何を見て・何に引っかかったか）【起票時必須】

`/design-sync`（2026-08-09・工程4 後の再同期）の **conventions header 実在検証**で出た。

検証そのものは**ドリフト 0 件**だった——header が名指しするクラス 27・custom property 2・部品/パーツ/hook・
props と union 値・**否定の主張**（`Container` に `inset` が無い等）まで全件が出荷物に実在した。
**「header が嘘を言っていないか」は緑。**

🟥 **引っかかったのは逆方向だった。**検証は「header → 出荷物」しか見ていない。
**「出荷物 → header」を数えたら 8 件が落ちていた。**

```
ds-bundle/components/**/ のカード 39 件
  − header が名指ししている部品
  = DescriptionList / Timeline / Breadcrumb / Tabs / FilterBar / FormLayout / PageHeader / PeriodSelect
```

★ **header の 2 層の列挙は「完全なリスト」の顔をしている**——
「This system ships two tiers. Both are real, shipped components — reach for either rather than
writing your own markup」と書いてあるので、**列挙に無い ＝ 存在しない**と読める。

## 2. 経緯と今の理解【起票時必須・「わからない」でもよい】

**問い**: 8 件を header に足すべきか。足すならどう足すか。

**そのまま足せない理由**（🟦 実績がある）:
[DR-0069](../DR/DR-0069-adding-prohibitions-to-the-header-degraded-the-output.md) —— 手8 で **禁止 3・語彙 0 を 842 バイト**足したところ、
**禁止した箇所は直ったが、触っていない `Container` / `Section` / `DataGrid` が出力から消えた。**
→ ロールバック済みで、**header は手7 の 6,832 バイトが最後に「効いていた」状態。**
つまり **header は「足せば足すほど効く」もの**ではなく、**総量か配置で相互作用する。**

**現在地**: 🟥 **どちらも確かめていない。**
- 8 件が本当に手組みされているのか（＝害が実在するのか）は**測っていない**。
  [OBS-0013](OBS-0013_部品があるのにインラインスタイルで組んだ.md) は同型の実例だが、**この 8 件で起きたわけではない。**
- 足したときに何が壊れるのかも**測っていない**（DR-0069 は「禁止を足した」ケースで、**部品名を足した**ケースではない）。

**何がわかれば解けそうか**:
1. **害の実在**: 8 件のうち 1〜2 件を名指しで使わせる指示を design プロジェクトに出し、**手組みされるか / 部品が使われるか**を見る。
2. **1 変数の投入**: 8 件をまとめてではなく **1 件だけ**（例: `Tabs` を Composed に 1 行）足し、
   **触っていない箇所が消えないか**を数える。🟥 **DR-0069 の教訓は「触った箇所ではなく触っていない箇所を数える」**（NOTES 見張り #15）。
3. **総量なのか配置なのか**: DR-0069 が総量（バイト数）由来なら、**足すぶんどこかを削る**必要がある。
   配置由来なら削らずに済む。**これは 2 の実験の設計を変える**ので先に見当を付けたい。

🟨 **急ぐ理由はある**——工程5（稼働表）以降も部品は増える。
**検体が増える前に測り方を決めておくほうが、変数が少ないうちに済む。**

## 3. 知識の結びつき ★主目的【棚卸しで埋める。insight は起票時から】

- 既に持っていた知識・経験：🟥 要確認
- 今回新しく得た・繋がった知識：🟥 要確認
- 結びついて生まれた気づき（できれば 1 行の一般則まで）：
  🟨 **仮説（本人未確認）**——**検証は向きを持つ。**
  header 検証は毎回「header → 出荷物」（名前が実在するか）を全件見てきたが、
  **「出荷物 → header」（実在するものが名指しされているか）は一度も数えていなかった。**
  🟥 これは 2026-08-08 の「**名前の実在は効果を保証しない**」（[DR-0090](../DR/DR-0090-token-classes-were-silently-dropped-by-tailwind-merge.md) 由来の検証方法への指摘）と
  **同じ「検証の方法そのものへの指摘」の 2 例目**に見えるが、**本人の確認が要る。**

## 4. 結論と保留

- **今の結論**：🟨 **header は書き換えない**（今回の同期では触っていない）。
  skill 側も「既存 header は書き換えず、ドリフトを報告して提案する」規定で、**repo の DR-0069 と一致している。**
- **保留・未確認**：
  - 🟥 **害が実在するか未測定**（8 件が手組みされる証拠はまだ無い）
  - 🟥 **DR-0069 が総量由来か配置由来か未特定**
  - 🟥 **`FilterField` は 8 件に含めていない**——カードが無い（story が無い）ので出荷部品ではない。[OBS-0014](OBS-0014_同一ファイルに2キーを向けたときconverterが何をするか.md) の対象
- **この結論が変わる条件**：
  上の実験 1（害の実在）で **8 件のどれかが手組みされたら**、埋める側に倒す。
  実験 2（1 変数投入）で **触っていない箇所が消えなければ**、残り 7 件も同じ形で足せる。

## 5. 却下した代替案【任意】

| 案 | 内容 | 却下理由 |
|---|---|---|
| A | 8 件をまとめて header の 2 層の列挙に足す | 🟥 **DR-0069 の再演になる。**手8 は 842 バイトで壊した。8 件ぶんはそれを超える見込みで、**壊れても原因の切り分けができない**（多変数） |
| B | header の「2 層」の列挙をやめ「`components/` を読め」に置き換える | 🟥 **届かない。**[DR-0064](../DR/DR-0064-design-project-receives-runtime-only.md)——デザイン側が受け取るのはランタイムだけで、`<Name>.prompt.md` も `guidelines/` も**読ませられない。**列挙が唯一の伝達路 |
| C | 何もしない | 🟨 **今回はこれ**（測っていないものを直さない）。ただし**工程が進むほど検体が増える**ので、先送りのコストは上がる |
